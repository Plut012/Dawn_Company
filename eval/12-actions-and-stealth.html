    4. Stage A: the game plays exactly as it did

    50 of 50 seeded matches gave the same digest before and after stage A. Combined digest before: 4c64e70ddfead1ba. After: 4c64e70ddfead1ba. Recorded 2026-11-18.

    Method. scripts/seeded.ts plays fifty fixed matches (seeds 1001 to 1050; 2, 3 and 4 players in turn, preset squads, every unit a seeded random legal order from orderOptions on its own player's view, leaning towards contact) and hashes, for each match, every round's full event list, every player's event list and the final state (SHA-256, first 16 hex digits). It was written and run before any rules code was touched, and its output saved. After stage A it was run again. The only thing left out of the hash was the new action field on the fire, launch, impact and treat events: information added to an event, not a change in what happens. The option lists are sorted before a choice is made from them, so the digest does not hang on the order orderOptions lists hexes in (that order did change for the medic). The fifty matches hold 440 units down, 113 ambushes sprung, 1,645 shots and 34 treatments, so the digest covers all five actions.

    The check is kept as src/rules/digest.test.ts. Stage B then changed the rules on purpose, so the test now pins the digests recorded after stage B (combined b26a7704205b4e3a; the comment in the file keeps the stage A history) and leaves nothing out of the hash.

    The grep the task asks for, run on the finished code (grep -rn "rifleman\|gunner\|sniper\|mortar\|medic\|treat" src/rules --include=*.ts, tests aside), finds eight lines: seven are the phase names 'treat' and 'mortar' as Phase values in resolve.ts, and one is the event type t: 'treat', emitted by the recover effect inside the effects table (src/rules/effects.ts). No unit id and no action id.

    5. Stage B: what changed in play

    For the designer's tuning, not a pass or fail. Two sets of matches, each played on the code as it stood after stage A (“before”) and on the finished code (“after”), 2026-11-18. The players are random, not clever: they do not know how to use stealth, so these figures show how much the new rule changes a game by itself, not how much a player could get out of it.

    Scripted: npx tsx scripts/seeded.ts --figures 300, seeds 1001 to 1300, straight through the rules. Bots: npm run bots -- --matches 300 --seed 12012, over real sockets against the real server. “Before” was run from a copy of the repository taken after stage A. A match plays differently from the first round in which the two rules differ, so the same seed is the same squads and the same dice for the players, not the same match. “In cover, in line” counts, at each planning moment, enemy units standing in woods or a building with one of the player's units in sight range and a clear line: the units only stealth can hide.

    What the figures say. Next to nothing moves: units down, ambushes and score per match are within a few percent. The reason is in the rule itself. Before, any unit in woods or a building was seen from 2 hexes. Now a unit that moved there is still seen from 2 (no change), one that kept still is seen from 1 (harder to see), and one that dashed is seen at any distance (easier to see than before). For players who move at random the last two cancel. The rule's weight falls on a player who chooses to hold still, which random players do not do on purpose.
